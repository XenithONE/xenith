# 0009 — 診断が教える（能動的知識添付）

- 日付: 2026-08-05
- 状態: **採択（5モデル並列レビュー後の改訂版）**
- 手法: 事前登録 P1〜P6 → `codex` / `grok` / `agy` / `opencode` / `cursor`（Auto）の
  5並列攻撃レビュー → 判定統合。**P2（住処）だけがほぼ無傷で生き残り、
  P1・P3・P4・P5・P6 は全て改訂または破棄された。**
- 前提: v1/v2 の再現事実 — ホール経由の受動チャネルは使われない（招待でも許可でも
  goals 発話 4〜5%）、docs 因子（シグネチャ知識）だけが +7〜15 pass@1 で2回再現、
  全モデルが「完全な推測→エラー→修復」の習慣を持つ。

## 1. 最重要の自己修正（レビューが暴いた2つの取り違え）

**(a) 成功定義のすり替え（grok・cursor・codex）。** docs 因子の実測価値は
**pass@1（事前知識）**である。本 RFC の介入は定義上 pass@1 に届かない
（失敗後にしか発話しない）。草案 §1 の「docs 因子の再現」は約束できない。
本 RFC が主張してよいのは**「シグネチャ知識の失敗後配達が修復を速めるか」**だけであり、
北極星（一発正解）は本 RFC では 1pt も動かない。診断がどれほど賢くても、
ステートレスな CLI は次の課題でまた推測から始める。**能動添付は北極星の代替ではなく、
修復コストの削減である** — この一文を README にも刻む。

**(b) 消費の未検証公理（cursor が命名）。** 「診断は必ず読まれる ⇒ 載せた
シグネチャは消費される」は v1/v2 から導けない。goals も「読めば有用」だったが
使われなかった。よって v3 は**消費オラクル**を必須とする: 各ラウンドの teaches 全文と
診断コードを記録し、次ラウンドの差分が添付シグネチャを採用したか
（識別子置換のみか・構造変更か）を判定できる形で保存する。

## 2. ベンチ契約の二分（codex の枠組みを採択）

- **Unaided one-shot** — 初回提出前は field guide 以外の動的情報なし。
  北極星（一発正解）の測定。teaches はここに一切関与しない。
- **Compiler-assisted repair** — 固定ラウンド・固定診断予算での最終成功と修復コスト。
  **本 RFC の測定対象はこちらだけ。** 名称は「oracle-backed repair」（opencode）。

情報境界（codex）: (1) 公開言語知識＝宣言シグネチャ・効果・引数名 /
(2) 文脈的絞り込み＝当該レシーバの API / (3) 局所合成＝スコープから到達する具体式。
**v3 は 1–2 のみ。3（producers）は境界を超えるため別 RFC・別実験。**

## 3. teaches の設計（P1/P2/P3 の置換）

### 対象（家系別に独立フラグ）

1. **XN3008 系（引数形状の誤り）** — 最高精度（呼び先が確定している）。
   呼ばれた関数/メソッドの完全シグネチャを1件添付。Xenith 固有の
   名前付き引数規則は Rust/TS 直感と衝突する最大の罠（agy）であり最優先
2. **XN2003（未知メソッド）** — レシーバ型のメソッド目録。
   「全シグネチャ＋8行で切る」の自己矛盾（4/5 指摘）は**有限契約**で解消:
   固定順（宣言順）で**最大6シグネチャ**＋超過時は `total_items`/`truncated` を明示。
   打ち切り時の CLI コマンド導線は**載せない**（死んだチャネルへの再招待 — 3/5 指摘）

**見送り**: XN3001 producers（5/5 — 型が合うだけの式は誤修復を誘発、境界(3)超え）。
XN3001 は既存の expected/found 表示のまま。XN2002 は**保留**（見送りの根拠は
「雑音」ではなく**失敗モードの頻度が未測定**であること — grok。§6 手順0 の
再分類で決める。将来の最小形は cursor 案＝一意に決まる場合のみの did-you-mean）。

### ワイヤ（構造化 — 表示文字列を入れない）

```text
teaches: [{ kind: "call_signature" | "available_methods",
            type: "...", items: [{ name, signature }],
            total_items: N, truncated: bool }]
```

- `schema_version` は 1 のまま。ただし (a) **tolerant-reader 契約**
  （未知フィールドは無視すること）を wire のモジュール文書に明文化し、
  (b) 応答に `features: ["diagnostic_teaching_v1"]` を追加して
  「旧コンパイラで無い」と「対応済みだが空」を区別可能にし、
  (c) 消費者互換テストを実装前に置く（codex/opencode/agy の折衷）
- 分量規律: 家系別の件数上限＋エントリのバイト上限＋
  **`check` 1回あたりの総量予算**（連鎖診断での雪だるま — agy の
  attention distraction と codex の総量指摘への回答）＋
  同一型の目録は1回だけ（重複排除）
- レンダリング位置は primary message の**直後**（cursor — 末尾注釈は
  goals と同じ無視経路に入る）。決定性の範囲は「teaches の構造と順序」に限定して定義

### フラグ

`--terse` は捨てる（意味が広すぎる — codex）。**`--diagnostic-teaching=off`** を新設し、
off 時の診断が on 時から teaches を引いただけ＝**バイト同一**であることをテストで保証。

## 4. v3 実験設計（P4 の置換）

草案の致命傷: v2 の「query」腕はプロンプトで goals を勧誘し続けるため、
「勧誘文言 × teaching」が完全交絡し、腕名の再利用は読者を欺く（5/5）。

- **全4腕から goals 勧誘文言を撤去**し、真の 2×2 にする:
  **docs {on, off} × teaching {on, off}**。teaching on/off 間でモデルに渡る
  round-1 プロンプトは完全同一。v2 との水準比較は**放棄を明言**（v3 内対比のみ）。
  ホール許可文は全腕同一のまま残す（v2 で無害と実証済み）
- 主 estimand（事前登録）: **no-docs 内での teaching ON−OFF** を
  rounds-to-green・最終緑率・消費オラクル（採用率・転写コスト）で見る。
  割付ベースを主解析とし、teaches が実際に発火した事例に条件付ける分析は
  記述に格下げ（事後選択 — codex）
- pass@1 は**サニティチェック**（teaching 間で不変であるべき）に格下げ。
  「プライミング検出器」という過大な名前は撤回
- 記録の拡張: RoundRecord に**診断コード列**と **teaches 全文**（発火時）を追加。
  トークン消費も記録し「トークンあたり修復成功」（agy の JIT 配送効率）を出せる形に
- 課題は t4 の6本を流用（凍結済み）。固定課題×オラクル診断の記憶交絡（opencode）は
  「同一課題を v1/v2 でも使った」比較上の限界として README に明記

## 5. 漏洩問題への態度（P5 の分割）

- **製品として**: 採用。正しいシグネチャを診断で教えるのはコンパイラの義務に近い
  （rustc の help と同型）。境界 (1)–(2) の情報は言語仕様の一部であり漏洩ではない
- **ベンチとして**: 「docs と対称」という草案の弁護は撤回（事前の広い表と
  失敗条件付きのピンポイント表は情報量もタイミングも別物 — 5/5）。
  測るものは「診断追従による修復」であり、成功は転写コスト
  （識別子置換のみ/構造変更）と併記して過大解釈を防ぐ

## 6. 実装順序（P6 の置換 — 検証順）

0. **v1/v2 の保存済み試行ファイル（scratch の .xn）を現行コンパイラで再検査し、
   失敗の診断コード分布を実測する**（codex — どの家系が未修復失敗を覆うかで
   優先度と XN2002 の要否を決める。行列を走らせるより桁で安い）

   **実測済み（2026-08-05、t4 試行 300 ファイル）**: 診断ゼロ 200・
   **XN2003 = 51 で圧倒的首位**・XN3001 = 25・パース系合計 55・XN2002 = 12・
   **XN3008 = 1**。結論: XN2003 が本命の配達先（優先実装）、XN3008 は
   精度は高いが発火頻度がほぼゼロなので同じ基盤の上に安価に足すのみ、
   XN2002 見送りはデータで正当化（XN2003 の 1/4 以下）。
1. 現行診断の byte-level 回帰スナップショット＋JSON 契約テストを固定（opencode）
2. 構造化 teaches ＋ `features` 表明 ＋ `--diagnostic-teaching=off` ＋
   バイト同一性テスト（中身はまだ空でよい）
3. XN3008 添付 → 決定的スナップショット
4. XN2003 添付（有限契約・重複排除・総量予算）
5. **健全性スモーク**: 固定の失敗コード×少数モデル×1修復ラウンドで
   「次ラウンドが添付を採用するか」を先に確認（grok/cursor — 28セルより桁で安い）
6. ベンチ v3（真の 2×2・28セル・resume 方式）
7. 結果が正のときだけ XN2002 最小形・XN3001 の扱いを別 RFC で

## 7. 却下された代替案（記録）

- **XN3001 への producers 添付**（5/5）— 型適合≠意味適合。連鎖診断で期待型自体が
  不確か。境界(3)の局所合成であり「漏洩ではない」弁護が成立しない
- **pass@1 をプライミング検出器に使う** — teaches は round 1 に存在せず論理不成立
- **8行上限＋`xenith query` 導線** — 行数は端末依存で契約にならず、導線は
  実測で死んだチャネルへの再招待
- **v2 と同一プロンプトの維持** — 表面的な比較可能性と引き換えに
  勧誘文言×teaching の交絡を抱え、構成概念の変化（促す→自発添付）を隠す
- **「診断に載せれば消費される」の公理化** — 消費オラクル無しの成功主張は
  「いつも通りの修復習慣」と区別不能
