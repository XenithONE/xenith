## 1. 先に決めるべきだった言語意味論（codex が最重要指摘）

### D1 — コンテナ読み出しは値意味論（コピー）である

`List.get` / `Map.get` / `keys()` が「コンテナに残したまま所有値を返す」のは、
ムーブ既定の言語では未定義だった（codex:「API 名や実装順より先に決めるべき」）。

**決定**: Xenith の観測可能な意味論は**値意味論**とする。コンテナからの読み出しは
**値のコピー**を返す。実装は共有（CoW / 将来の ARC）で最適化してよいが、
観測結果はディープコピーと区別できてはならない。これは既存インタプリタの
値意味論（構造体・クロージャで実測済み）と一致し、当初計画の
「値セマンティクス + ARC（コンパイル時除去）」路線の明文化である。
将来のムーブ/アフィン検査は「コピーを新しい値として扱う」形でこの上に載る。
**参照・借用・ビューは存在しない。**

### D2 — String は Unicode スカラー値の列

`len()` はスカラー値の個数。`split` / `trim` もスカラー値単位で動く。
`trim` が除くのは ASCII 空白（space / tab / CR / LF）のみ。
バイト長・書記素クラスタ API は持たない（必要になったら別名で足す。
`len` の意味は永久にスカラー数）。

### D3 — 関数値は存在しない

field-guide に一等関数・クロージャ型・関数型パラメータは無い。
`sorted_by(compare: fn(T,T) -> Int)` は「最小 std の皮を被った高階関数導入 PR」
（grok）であり削除。高階関数は将来の独立 RFC（その際は `Ordering` enum・
コールバックの効果規則・`a - b` トラップ問題を先に設計する — codex）。

### D4 — 静的メソッド構文は存在しない

`Map.new()` は関連関数構文の新設だった（codex）。構築はプレリュードの
**ジェネリック自由関数**で行う（ジェネリック自由関数は既存機構）:

```xenith,planned
fn empty_map<K: Eq + Hash, V>() -> Map<K, V>
```

`let m: Map<String, Int> = empty_map();` — 型引数は期待型シーディング
（0006）から決まる。注釈が無ければ 0006 §1-1 と同じ「注釈が必要」エラー。

## 2. スコープ（P1 の置換）

**本 RFC は List / Map / String のメソッドだけを導入する。**

for-in・Range は除外（5/5）。理由の核: (1) `for item in xs` の束縛意味論が
D1 決定前は未定義だった、(2) P1 は「Map も3形に含む」と言いながら Map 走査には
タプル型が必要で、**この言語にタプルは無い**（grok が矛盾を発見）、
(3) 反復は `while` + `len` + `get` で全課題が書ける。
Range 専用糖衣（opencode/codex 案）も含め、反復構文は**別 RFC** に分離する。

## 3. API 表面（P6 の置換）

### 命名の裁定

**慣習名を維持する**（codex:「訓練データゼロは既存言語からの転移まで拒絶する
意味ではない。`len`/`push` の独自語化は北極星に逆行」）。ただし命名規則
（0001 原則6）に**裸動詞の許可リスト**を追加し、表外の動詞は発明されない
ことを field-guide に明記する: `len` `push` `pop` `get` `insert` `remove`
`replace` `split` `trim` `sorted` `keys` `concat` `join`。
Bool を返すものは規則どおり `is_` / `has_` / `contains` / `starts_with`
（`contains`/`starts_with` は許可リスト掲載の慣習例外）。
**Map だけは `has_key`** — 「キーの包含」と「値・部分列の包含」を
名前で区別する（codex + grok 合意点）。

事前学習リークで実験が汚れる問題（grok/cursor/opencode）への答えは
命名の歪曲ではなく**測定の分離**（§5: 実用試験と機構試験）。

### List<T>

| メソッド | シグネチャ | 規定 |
| --- | --- | --- |
| `len` | `() -> Int` | |
| `is_empty` | `() -> Bool` | |
| `push` | `(item: T) -> Unit` | `var` 束縛必須・in-place・末尾追加 |
| `pop` | `() -> Option<T>` | 末尾除去。空なら `None` |
| `get` | `(index: Int) -> Option<T>` | 負・範囲外は `None`。値のコピー（D1） |
| `replace` | `(index: Int, value: T) -> Option<T>` | 旧値を返す。範囲外は `None` で**無変更**（codex 案 — `set -> Bool` は P3 自己違反だった） |
| `contains` | `(item: T) -> Bool` | `T: Eq` |
| `sorted` | `() -> List<T>` | `T: Ord`。新 List・安定。Float は境界で弾かれる（0006 §3） |
| `concat` | `(other: List<T>) -> List<T>` | 新 List |
| `join` | `(sep: String) -> String` | **`T: Text` 境界**（cursor 案 — 封印済み性質の再利用。特定型引数の特殊メソッドという型系の汚れを避ける） |

構築: `[1, 2, 3]`・`[]`（期待型必須）。

### Map<K: Eq + Hash, V>

| メソッド | シグネチャ | 規定 |
| --- | --- | --- |
| `len` | `() -> Int` | |
| `is_empty` | `() -> Bool` | |
| `insert` | `(key: K, value: V) -> Option<V>` | 旧値を返す。`var` 必須 |
| `get` | `(key: K) -> Option<V>` | 値のコピー（D1） |
| `remove` | `(key: K) -> Option<V>` | |
| `has_key` | `(key: K) -> Bool` | |
| `keys` | `() -> List<K>` | 挿入順の**スナップショット** List |

`values()` は落とす（`keys` + `get` で導出可能。最小性）。
構築: `empty_map()`（D4）。

**挿入順の規範仕様**（P4 採択 + codex/agy の条件）:
既存キーへの `insert` は位置を変えず値だけ置換（格納済みキーも置換しない）。
`remove` は順序保存（shift）。remove 後の再挿入は末尾。`keys()` の並びは
この規則の帰結として常に決定的。Map の `==` は**順序を無視した**キー値対応
（codex: 表示順と等価性を混同しない）。`Float` は `Hash` を持たないため
**キーにできない**（field-guide に1行で明記）。構造的導出は
「`a == b` ならばハッシュも等しい」を常に保証する（コンパイラ導出のみなので
成立が機械的に守られる）。

### String 追加

| メソッド | シグネチャ | 規定 |
| --- | --- | --- |
| `len` | `() -> Int` | Unicode スカラー数（D2） |
| `split` | `(sep: String) -> List<String>` | **無損失**: `xs.join(sep:)` で必ず元に戻る。連続区切りは空文字列を保持、`sep = ""` はスカラー毎に分割（`chars` の代替） |
| `trim` | `() -> String` | ASCII 空白のみ（D2） |
| `try_to_int` | `() -> Result<Int, Error>` | 受理: 任意個の ASCII 空白 ± `[+-]?[0-9]+`。桁区切り・小数点は `Err`。`Int` 範囲外も `Err`（トラップしない） |
| `starts_with` | `(prefix: String) -> Bool` | |
| `contains` | `(sub: String) -> Bool` | |

**削除**（P6 から）: `sorted_by`（D3）・`chars`（`Char` 設計が先。
`split(sep: "")` が代替）・`reversed`・`repeat`・`values`・`set`。
std は測定のために膨らませない（codex:「プロダクト設計と測定装置の分離」）。

## 4. 実装順序（P9 の置換 — 垂直切り、5/5）

各スライスは parser → sema → interp → 診断 → **goals/producers 統合** →
負例テストまでを一気に通す。「型だけ存在して実行できない」中間状態を作らない。

1. **L0（装置の煙試験）**: List の `len`/`get`/`push` + リテラル + 候補統合。
   完了条件: **「`goals` が期待型に対して `push`/`get` を候補に出す」がテストで緑**
   （grok: オラクルが死んでいれば以降を作っても第2仮説は測れない）
2. **L1**: List 残り（`sorted` は Ord 境界のみ）
3. **S**: String 拡張 + parse 系課題が書けることを確認
4. **M**: Map + `empty_map`
5. field-guide 改訂 → 課題凍結 → 測定（§5）

負例を各スライスに含める: 空コンテナ・負添字・非 `var` レシーバへの `push`・
境界違反（`Float` ソート・`Float` キー）・Unicode 混在・Map 再挿入順。

## 5. 分離実験の再設計（P7 の置換 — 5/5 で旧設計は棄却）

旧設計の致命傷（全員が独立に指摘）: (1) full-pack から API 表を抜き
「推測するな」と命じるのは対照群の弱体化であり、勝っても「情報を奪えば負ける」
の確認にしかならない、(2) hole-guided には goals・候補・多ターン修復が
**束で**入っており因果識別不能、(3) 慣習名のままでは表を隠しても事前学習が
名前を当て、天井が再構築される、(4) 「5ポイント」は n=42 の対応セルで
正味3セル差 = McNemar 正確検定 p≈0.25 であり判定規則にならない（codex 実算）。

### 5-1. 条件 — 2×2 要因計画（opencode 案 + grok/codex の識別要求）

| 条件 | ガイドの API 表 | `goals`/`producers` |
| --- | --- | --- |
| `docs` | あり | なし |
| `query` | なし | あり |
| `docs+query` | あり | あり |
| `blind` | なし | なし |

**全条件で同一**: 修復ラウンド上限（4）・プロンプト骨格・`check`/`run` の
診断フィードバック・課題文。非対称ナッジ（「推測するな」）は**どの条件にも
入れない**（grok 穴2）。条件間の差は「API 表の有無」と「goals/producers 出力の
有無」だけ — 主比較 `query` vs `blind` が問い合わせ機構の価値を、
`docs+query` vs `docs` が「文書があっても問い合わせが足すもの」を単離する。

### 5-2. 測定の分離（codex の裁定）

- **実用試験（本 RFC のスコープ）**: 自然な std 名の課題6本。任意の正解
  プログラムを許す（stdout 判定）。事前学習の名前当ては `blind` 条件の
  成績として**それ自体を測定**する（隠さない）。
- **機構試験（後続、課題は本 RFC で凍結しない）**: ベンチ専用の合成 API 名で
  「署名発見能力」だけを測る。本番 std の名前は実験のために歪めない。

### 5-3. 事前凍結（codex/opencode の評価者独立性要求)

課題の完全文面・期待 stdout・参照解・ラウンド上限・採点規則を、
**候補ランキングの改良より前に**コミットで凍結する（ハッシュが独立性の証明）。
課題ファイル名はブラインド ID（`t4-01`〜`t4-06`）。課題文は目的を書き、
std のメソッド名を動詞として書かない（grok 穴8 の緩和。完全排除は不可能と
記録した上で）。

### 5-4. 課題（P8 改訂）

| ID | 内容 | 旧名からの変更 |
| --- | --- | --- |
| t4-01 | 文を区切り、出現回数を数え、キー昇順で `word:count` 出力 | — |
| t4-02 | `"12, 34, x, 56"` を区切り→整形→整数化、失敗をスキップして合計 | — |
| t4-03 | 単語群を長さで分類し `Map<Int, List<String>>`、整形出力 | — |
| t4-04 | 重複除去（Map を集合に）→ソート→結合 | — |
| t4-05 | 構造体リストから**明示ループ**で最大要素を選ぶ | max-by を置換（`sorted_by` 前提だった） |
| t4-06 | Map の逆引き表を作る（値→キー、衝突は先勝ち） | checkerboard を置換（構文課題で API 発見ではなかった — codex） |

### 5-5. 判定と報告（「5ポイント」の放棄）

- 本測定は**探索的パイロット**と明記する（codex）。数値閾値による
  「支持/不支持」の二値判定はしない。
- 報告: 課題別・モデル別・全体（マイクロ）の3集約（grok）＋条件間の
  対応セル（不一致ペア数を McNemar 正確検定の記述統計として併記。
  検定の限界は Fagerland et al. 2013 を引用済み — codex）
- **オラクル命中率を必ずログする**: `query` 系条件の成功課題で、最終解が
  使ったメソッドを `goals`/`producers` が事前に提示していたか（grok 穴7・
  codex）。これが低ければ「仮説が偽」ではなく「候補機構が未熟」と切り分ける。
- 確認実験（confirmatory）は機構試験と合わせて別 RFC。

## 6. 却下された代替案（記録）

- **for-in 全面導入 / Range 専用糖衣**（P1・opencode/codex の縮小案も含め）
  → 反復構文は別 RFC へ。D1 決定後なら List for-in は定義可能になったが、
  「課題1本のために構文を焼くのはスコープ逆転」（cursor）
- **`sorted_by`** → 高階関数の密輸（D3）
- **非慣習名への全面改名**（grok/opencode/cursor の一部提案）
  → 北極星に逆行（codex）。実験清浄性は測定の分離（§5-2）で得る
- **`String.join` 自由関数 / `List<String>` 特化 join** → `T: Text` 境界が
  既存機構で同じ効果を型系を汚さず達成（cursor）
- **ソート順 Map・順序未規定 Map** → stdout 固定ベンチと決定性原則に反する
  （opencode の反対は「観測可能仕様の早期固定」への警告として記録。
  挿入順は**仕様**であり実装詳細ではない、が本 RFC の回答）
- **「5ポイント閾値」** → 統計的判定規則として不成立（codex 実算）。
  探索的パイロット + 記述統計 + オラクル命中率へ置換
