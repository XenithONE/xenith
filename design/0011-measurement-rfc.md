# 0011 — 測定RFC: tier-5 制約付き統合と api-dump 条件

- 日付: 2026-08-07
- 状態: **採択（5モデル並列レビュー後の改訂版）**
- 手法: 事前登録 P1〜P6 → codex / grok / agy / opencode / cursor(Auto) の5並列攻撃
  レビュー → 判定統合。**草案は大破した。** 名称・課題構成・プライマ・仮説の閾値が
  作り直しになり、狙いの中心が「三条件の完成」から
  **「full-pack が複数ファイルでスケールしなくなる崖の初測定」**へ移った。

## 1. 課題設計 — tier-5 は2族6課題（constrained integration）

**tier-5 が測るのは消費側規律と配線であり、境界の設計能力ではない**（codex の
測定可能性リストを §8 に転記）。名称も「複数ファイル開発」ではなく
constrained integration とする。

- **t5a 実装型（4本）**: スケルトン（`xenith.toml` + 凍結 `src/main.xn` + 提供モジュール）
  を与え、モデルは指定1パスの新規ファイルを書く。`main.xn` が呼び出し契約を宣言する
- **t5b 配線型（2本）**: 提供モジュールは完成・凍結。モデルは**呼び出し側
  `src/main.xn` そのものを書く** — use 宣言・完全修飾参照・効果宣言・main 規則を
  自力で成立させる。XN2007 / XN2002+use-fix / 未使用 use が本線になる課題族
- 観測点の割当表（凍結物に含める）: XN7008 誘惑構図 = t5a×1（**正解パスは境界越え
  なしで到達可能・境界越えが最短に見える罠**を仕様に明記 — cursor）、外部 enum 網羅
  match = t5a×1、Result+効果整合 = t5a×1、use 配線 = t5b×2
- 隠しテストは stdout 一致。**参照解は提供 pub API を実際に呼ぶことを verify の必須
  観測にし**、ローカル再実装で stdout だけ合わせる逃げ道を課題側で狭める
- 実装前凍結・参照解 verify・中立ディレクトリ・ツール禁止 CONTRACT は従来どおり

## 2. 条件 — 3×2 要因（docs 形態 × teaching）・252走

| 軸 | 水準 |
|---|---|
| docs | **guide**（field-guide 全文） / **api**（機械生成 api-dump） / **none** |
| teaching | on / off（0009 の teaches ブロックのみを切替。**診断本文と fix は全腕同一** — バイト同一性テスト済み。teaching は fix 束ではない — codex への回答） |

- 全腕共通プライマは **P-syntax のみ**（fn / let / match / 効果 / 名前付き引数。
  **モジュール・use・完全修飾・pub を含まない**。例示は課題外の架空名）。
  モジュール規律の知識源は docs 腕・診断・teaches だけにする
- 6腕すべてに推定対象を宣言:
  (1) **三チャネル孤立比較** {guide+off, api+off, none+on} — 0002 §10 の実務版
  (2) teaching の複数ファイル再現 {none+on vs none+off}
  (3) 相互作用 {api×on/off vs none×on/off の方向付き差分}
  (4) 製品スタック比較 {guide+on vs api+on}（文書チャネル比較ではないと明記 — codex）
- 統計: **固定7モデル×6課題への記述統計**と宣言（母集団一般化をしない）。
  pass@1 の対応比較はモデル層で層別 McNemar。rounds は分布と予算内green数を
  モデル別・課題別の生カウントで公開。打切りは既存ベンチのラウンド上限規則を
  そのまま引用し、未到達は打切りとして符号化（新しい閾値は発明しない）
- **診断は初回候補が出るまで一切配達しない**（pass@1 の純度 — codex）。
  teaching の効果は「診断曝露があった走」に条件付けた集計を併記する

## 3. 入力契約 — 腕ごとの全バイト・マニフェスト（最危険への回答）

初回モデル呼び出しに入る情報を列挙固定する。**これ以外は入らない**:

1. 共通: P-syntax プライマ / 課題指示 / 書込先パス / CONTRACT
2. t5a: **凍結 `main.xn` の全文**（呼び出し側が仕様である、と宣言する）。
   **提供モジュールのソース本文は不可視**（0011 の既定。可視軸は後続 RFC）
3. t5b: 提供モジュールのソース本文は不可視。課題指示に出力仕様のみ
4. docs 腕: guide 全文 or api-dump（どちらも同一位置に挿入）。none は無し
5. プレリュード表 api-table.md は **docs 系2腕のみに含める**（guide には元々含有・
   api には連結）。none 腕には入れない — 「none = プライマ以外ゼロ」を厳密化
6. 修復ラウンド: check/run の診断出力のみを追記（teaching on/off はここで分岐）

ソース不可視の帰結を引き受ける: none 腕は外部 API を診断経由でしか知り得ない。
**それこそが「診断だけで零知識から緑まで運べるか」という本 RFC の最強の問い**である。

## 4. 仮説（改訂版・方向のみ・閾値なし）

- **H1a（t5a・反転した予測）**: pass@1 で **api ≥ guide**。guide は言語一般を運ぶが
  課題固有 API を構造的に含み得ない。full-pack は複数ファイルでスケールしない、
  というのが本 RFC の中心予測。逆転（guide 勝ち）が出たら「シグネチャ以外の散文が
  複数ファイルでも支配」として 0012 の議題に登録
- **H1b（t5b）**: 方向を固定しない（探索的）。guide は use 規律を運ぶが対象 API を
  知らず、api は表を運ぶが規律を教えない — 両腕とも部分盲目
- **H2**: none+on は none+off より rounds-to-green 分布で改善（0009 の一般化）。
  取り下げは二段: 全体で改善しなければ一般性主張を取り下げ。特定診断コードに
  限定されるなら限定的に撤回（grok の部分取り下げ規則）
- **H3**（P-syntax のみ配布下）: 初回生成は use/修飾規律違反を含む（コード別に
  集計: 項目use・裸参照・mod宣言・use漏れ）。診断後の次ラウンド修復率を別掲。
  収束しない場合は **(i) 0010 設計 (ii) 診断文面 (iii) 課題過負荷** の三分岐で
  記録し、設計バグの断定はしない（0012 の議論開始条件）
- **H4**: Δnone=(on−off|none) と Δapi=(on−off|api) の方向付き差分で定義。
  予測: rounds で Δapi < Δnone（代替方向）。**H4-b（逆転・agy/opencode）**:
  api は「何があるか」、teaches は「どう繋ぐか」で補完し Δapi が残る — 成立したら
  代替関係の主張を単一ファイル限定に縮める
- **H0（操作確認 — grok/cursor）**: none+off が最悪群。崩れたら課題が易しすぎるか
  計器故障を疑い、本測定を止める

**改訂1（パイロット後・本測定前に事前登録）**: パイロット12走で teach 発話が全腕0だった。
切り分けの結果、配管は健全（プロジェクトモードでもプレリュード型 XN2003 は on で
AvailableMethods が付き off で消える — 実射確認）。真因は**出荷済み teaching の適用範囲**:
モジュール所有型は「メソッド」を持たない（API は自由 pub fn）ため、`x.stow(...)` 型の誤りに
対して当該モジュールの pub fn を教える teach が存在しない。0011 は出荷済みコンパイラを
そのまま測る（計器・課題・プロンプト変更なし）。したがって **H2 の teaching 効果は
プレリュード XN2003・XN5001 証人・曖昧 XN2002 の use_candidates が担い、モジュール API の
発見はガイド/dump/診断本文+fix（両腕共通）が担う**という適用範囲マップの下で読む。
teaching 軸が僅少に出た場合、それは「診断配達の不成立」ではなく「teaching 適用範囲が
モジュール API に未拡張」の測定であり、拡張（unknown-member-on-module-type →
モジュール pub fn の CallSignature 提示）は 0012 の第一議題として登録する。

## 5. 運用規律

- **セッション独立の明文化**（opencode の最危険への回答）: resume はハーネス走行
  台帳の再開であり、**モデル呼び出しは全走で新規セッション・文脈持越しゼロ・
  中立ディレクトリ**。修復ラウンドの文脈は当該走の内部にのみ蓄積
- パイロット（1モデル×2課題×6腕=12走）後に変更してよいのは**計器のみ**
  （ハーネスバグ・ログ・パース）。課題・プロンプト・dump に触れたら再凍結し、
  改訂として本 RFC に追記する（黙って直さない — codex/grok）
- 欠損・再開順の偏り（強いモデルから埋まる等）を避けるため、走行順はモデル×課題×腕
  の固定シャッフル表を凍結する

## 6. 成功の解釈を縛る事後観測（cursor の最危険への回答）

合否には使わない事前登録の静的観測を summary に列挙する:
完全修飾率 / 禁止パターン試行（項目use・裸参照・mod）/ XN7008 の出現と直後の行動
（修正 or 別設計へ逃走）/ use 追加が fix 採用か手書きか / **緑だが提供 API 未使用**
フラグ。「緑 = 0010 成功」の等式を裸で使わない。

## 7. api-dump の生成（旧 retrieved）

- 名称は **api**。0002 §10 との対応は「retrieved の内容近似 = 検索オラクル上界。
  検索品質は未測定」と一文で限定し、**「三条件完成」とは呼ばない**
- 生成器はベンチ内エクスポータ（xenith-bench のサブコマンド。コンパイラのクレートを
  直接使う。製品 CLI `xenith api` は測定後の別 RFC — 測定がスキーマを検証してから
  製品が追従する順序）
- 内容: 提供モジュールの pub fn 完全シグネチャ・pub struct/enum 完全定義・効果集合。
  決定的並び順・生成器バージョンと生成物ハッシュを記録・手編集禁止・課題と共に凍結
- **測定前ゲート（cursor）**: 参照解が必要とする表面が dump に全部含まれることを
  参照解 verify と突き合わせるゴールデンテスト。壊れた地図で本測定を走らせない

## 8. 入れないもの・測っていないと明言するもの

- 測らない（codex のリストを正典として転記）: モジュール分割・依存方向・公開面の
  設計 / 複数ファイル協調変更 / 循環回避 / 呼び出し側と実装側の同時修復 /
  リポジトリ探索 / 段階的変更。**これらは tier-6 以降の別 RFC**
- 本物の RAG（検索・選択・取りこぼし）/ ソース可視軸（0011 は不可視固定・可視は後続）
- 新診断・言語変更（0012）・モデル集合の変更・従量課金 API
- 実装順: 課題6本凍結（t5a×4, t5b×2）→ api-dump エクスポータ+ゴールデンゲート →
  bench プロジェクトモード → パイロット12走 → 本測定252走 → summary + README

## 9. 却下された草案要素（記録）

- **「retrieved」名称** — 検索・選択・取りこぼしが存在しない完全ダンプを retrieved と
  呼ぶと、後日「検索が効いた」と誤読される（5/5）
- **モジュール節入り共通プライマ** — H3 を先回りして潰す「治療」（4/5）
- **1ファイル穴埋め6本一本槍** — use-fix 経路を自分で干上がらせ、仮説と課題が矛盾
- **H1「課題1個分以内」** — 単位不明の閾値発明。等価マージンは製品判断から導出
  できない限り書かない
- **guide+on vs api+on を「文書チャネル比較」と呼ぶこと** — 実態は製品スタック比較
- **`xenith api` の測定前製品化** — スキーマが事実上の言語表面になり測定と仕様が循環
