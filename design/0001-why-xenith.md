# 0001 — なぜ Xenith を作るのか

- 日付: 2026-08-01
- 状態: **一部が 0002 により改訂済み**。本文書は当初の動機・目標・非目標の記録として残す。
  草案10項目のうち 1・2・3・4 は [0002](0002-design-review.md) で変更された。

---

## 1. 動機

既存の言語は「人間が読み書きしやすいこと」を前提に設計されている。
コードの書き手の相当部分がLLMになった今、その前提は部分的にしか成り立たない。
LLMの失敗様式は人間のそれと違う。

ただし素朴な発想——「LLMが読みやすい構文を作る」——は**ほぼ誤り**である。
LLMのある言語での流暢さは訓練データ量に支配されており、新言語のそれはゼロだからだ。
文法を綺麗にしても Python には勝てない。むしろ新奇な構文は事前学習の重みと戦うため、
負荷がかかると Python/Rust の癖に退行する（この論点の詳細は 0002 §2）。

したがって賭ける対象は構文ではない。**コンパイラである。**

## 2. 目標

1. **一発の正しさ** — LLMが最初の試行で正しいコードを書ける確率を最大化する
2. **修復の速さ** — 間違えたとき、緑になるまでの往復回数を最小化する
3. **拡張性** — ゲーム（フレーム予算・予測可能な遅延）とサーバー（大量IO）の両方に耐える
4. **個人で完走可能** — 単独の維持者が現実的に到達できる設計に留める

目標1と2は測定可能でなければならない。`bench/ai/` がその測定装置であり、
言語設計の変更はその数値が動いたかで判断する（0002 §10）。

## 3. 非目標

- **実行性能の頂点を狙わない。** 正しさと予測可能性を優先する。
- **借用チェッカを持たない。** ライフタイム注釈をユーザーコードに登場させない。
  全プログラム規模の生存期間推論はLLMが最も高頻度で失敗する領域だから。
- **ユーザー構文マクロを持たない。** ハルシネーション面と可読性の両方で害が大きい。
  （スキーマ束縛・RPCスタブ・直列化のための**コンパイラ所有の生成器**は別枠で持つ。
  生成物はコミットして可検査にする。0002 §8）
- **v1.0 まで独自パッケージレジストリを作らない。** 依存は git 直参照。
- **万人向けを狙わない。** 人間可読性は放棄しないが、設計上の対立が起きたときは
  「コンパイラがモデルを誘導できるか」を優先する。

## 5. 名前

`Xenith` は維持者のハンドル `XenithONE` に由来する。
2026-08-01 時点で同名のプログラミング言語は存在せず、crates.io でも未取得だった。

CLI 名は当初 `xen` を予定していたが**変更した**。
`xen` は crates.io で使用済みであり、より重要な理由として Xen ハイパーバイザが
同名のコマンドを持つため実運用で衝突する。CLI は `xenith`、crate 接頭辞は `xenith-*` とする。
ソースファイルの拡張子は `.xn`。
