## 1. 全員一致：双方向型検査（5/5）

`check`（期待型を下ろす）と `synth`（型を上げる）の2判断で構成する。

**なぜこれが正しいか。** ホールのために特別な機構を足すのではなく、
**`check` モードはあらゆる位置で「要求される型」を保持している**ので、
ホールの目標が通常の走査の副産物として落ちてくる。

```rust
fn check(&mut self, expr: &Expr, expected: &Type, ctx: &Ctx);
fn synth(&mut self, expr: &Expr, ctx: &Ctx) -> Type;
```

ホール規則はこれだけである：

```rust
ExprKind::Hole { name } => {
    self.goals.push(Goal {
        expected: expected.clone(),
        in_scope: ctx.env.snapshot(),
        allowed_effects: ctx.budget.clone(),
        ..
    });
    // 期待型として通る。診断は出さない。
}
```

全プログラム推論（HM）は採らない。局所推論の禁を破るうえ、
「葉を直すと根の型が反転する」という修復の毒を再導入するため。

### 1-1. 期待型の無いホールは**ハードエラー**にする（grok・cursor）

`let x = ??;` のように `synth` 位置に現れたホールは、推論変数にしない。
**「注釈が必要」という診断を出す。** 局所推論を選んだ以上、`x` の型を虚空から発明しない。

- `let x: Config = ??;` → 動く。期待型は `Config`
- `let x = ??;` → エラー。「この束縛に型注釈が必要」

**これは欠陥ではなく仕様である。**

### 1-2. 型位置のホールは別の判断（cursor）

`fn f(x: ??)` は式のホールとは別に `TypeGoal` を出す。
本体の期待型を `Type::Hole` にしてはならない — 候補が「あらゆる式」になって無意味になる。

## 2. 全員一致：`Error` と `Hole` を分ける（5/5）

| 種別 | 意味 | 診断 | 目標 |
|---|---|---|---|
| `Type::Error` | 既報告の失敗の毒。**あらゆる型と適合** | **決して出さない** | 出さない |
| `Type::Hole(id)` | 意図的な欠落。**エラーではない** | 出さない | **出す** |
| その他 | 実際の型 | 通常どおり | — |

**報告規則**: 両辺が具体型（どちらも `Error`/`Hole` でない）のときのみ報告する。
毒はデータフローの辺に沿ってのみ伝播させ、関数全体を不明にはしない。
呼び出し先の型が `Error` なら、その呼び出しの引数不一致は黙るが、**兄弟の部分木は検査を続ける**。

> cursor の指摘：「適合判定で両者を同一視するのは正しい。**目標の生成で同一視してはならない。**」
> `is_unknown()` を参照してよいのは診断だけである。

## 3. 【方針転換】「トレイトを持たない」を修正する

**5モデル中5モデルが「制約機構ゼロは汎用言語として成立しない」と判定した。**

> 「**絶対的な『トレイト無し』は成立しない。** `==` / `sort` / `Map` / `to_text` を
> 局所的なエラーで扱いたいならなおさらだ。」（grok）
>
> 「**あなたのカーネル自身がすでに `Eq` と `Copy` を密輸している。**
> その穴を先に塞がないと `Map` / `sort` / `==` がモデルに嘘をつく。」（cursor）

cursor の指摘は正しい。[0003](0003-semantic-kernel.md) の表は
「`==` は `Eq` を宣言した型の構造的等価」と書いているのに、`Eq` を定義していなかった。
**自分の仕様が、定義していない概念に依存していた。**

### 3-1. 採択：封印された型の性質（sealed predicates）

トレイトでもタイプクラスでもない。**コンパイラが決める型の性質**であり、
**利用者が実装を書く構文は存在しない**。

```text
Eq      等価比較できる
Ord     全順序を持つ
Hash    Map の鍵になれる（Eq を含意する）
Copy    暗黙にコピーされる（スカラのみ）
Text    デバッグ表示できる
```

境界として書ける：

```text
fn contains<T: Eq>(items: List<T>, value: T) -> Bool
fn sorted<T: Ord>(items: List<T>) -> List<T>
fn get<K: Eq + Hash, V>(map: Map<K, V>, key: K) -> Option<V>
```

**なぜトレイトの費用を払わずに済むか。** 実装は型の構造から**一意に決まる**。
選択肢が存在しないので、「どの実装が選ばれるか」というLLM最頻出の誤りが**原理的に起きない**。
コヒーレンスも孤児規則も特殊化も関連型も無い。判定は探索ではなく**真偽表の参照**である。

`trait` は予約語のまま**永久に予約**しておく。開いたタイプクラス系は導入しない。

### 3-2. 満足規則

| 型 | Eq | Ord | Hash | 備考 |
|---|---|---|---|---|
| `Int` `Char` `Bool` | ✅ | ✅ | ✅ | |
| `Text` | ✅ | ✅ | ✅ | |
| `Float` | ✅ | ❌ | ❌ | §3-3 |
| `()` | ✅ | ✅ | ✅ | |
| 構造体・列挙 | 全フィールドが満たすなら ✅ | ❌ §3-4 | 全フィールドが満たすなら ✅ | |
| `List<T>` `Option<T>` `Result<T,E>` | 要素が満たすなら ✅ | ❌ §3-4 | 要素が満たすなら ✅ | |
| `Shared<T>` | ❌ | ❌ | ❌ | 同一性は `is` を使う |
| 関数型・権能・可変セル | ❌ | ❌ | ❌ | |

**導出は自動で、構造的で、再帰的。** `derive` 句は書かない。

> ⚠️ **反対意見を記録する。** codex と cursor は明示的な `derive Eq, Hash` を推した
> （API意図が文書化される、フィールド追加で性質が黙って変わらない）。
> 自動導出を採ったのは、①定義が一意なので何も「選んで」いない
> ②モデルが覚えるべき構文が1つ減る ③フィールド追加で性質が失われた場合、
> **使用地点で原因のフィールドを名指しした精密なエラーが出る**、の3点による。
> ベンチで再検討する。

### 3-3. `Float` は `Ord` でも `Hash` でもない（codex と grok が独立に指摘）

**NaN のため IEEE の浮動小数点の等価は同値関係ではない。**
したがって全順序の根拠にも、ハッシュ鍵の根拠にもできない。

- `Float: Eq` — 認める。IEEE 準拠。`NaN != NaN`
- `Float: Ord` — **認めない**。`sorted()` は `Float` の `List` に使えない
- `Float: Hash` — **認めない**。`Map<Float, V>` は作れない

`sorted_by(compare: total_order_float)` を使う。
これは私が気づかずに出荷しかけた**実際の正しさの問題**だった。

> cursor は `Float: Eq` すら拒否して `approx_eq` を強制せよと主張した。採らない。
> `==` が浮動小数点に使えない言語は転移を大きく損なう。IEEE の挙動は文書化する。

### 3-4. `Ord` はスカラと `Text` にのみ自動導出する

構造体の順序を宣言順の辞書式で導出すると、**フィールドを並べ替えただけで
ソート結果が黙って変わる**。opencode の言う「恣意的なAPI挙動」である。

したがって集約型に `Ord` は導出しない。順序が要るなら明示する：

```text
players.sorted_by(compare: by_score)
```

**拡張点はトレイト実装ではなく関数引数である。** `xs.sort()` を読んだモデルは
どの実装が効いているかを知らねばならないが、`xs.sorted_by(compare: by_score)` は
**何が走るかを行内で読める**。局所完結性そのもの。

### 3-5. `to_text` は全域（cursor）

デバッグ表示は**あらゆる型に対して構造的に全域**とする。制約は**アルゴリズムのため**にあり、
デバッグ出力のためではない。利用者向けの整形は明示的な関数で行う。

### 3-6. これはフロントエンドの未完成を意味する

境界構文 `<T: Eq + Hash>` はパーサに存在しない。次に実装する。

## 4. ホール候補の生成と順位付け

**合成ではなく列挙してから絞る。** 深さは1、稀に2。

**候補プール（〜20件まで生成して5件に絞る）**
1. 型が完全一致するローカル・引数
2. その型のコンストラクタ・列挙の変種（引数は入れ子のホールにする）
3. 実体化後の戻り値が一致する関数（効果が予算以内のもののみ）
4. 型が一致するフィールド射影 `x.f`
5. `Option`/`Result` のときのみ深さ2の包み込み：`Some(??)` `Ok(??)`

**即座に除外**: 効果が予算を超える／ムーブ済みの束縛を使う／`Type::Error` を含む／
同じ頭部への再帰展開。

**順位付け**（重みは初期値。ベンチで調整する）

| signal | weight |
|---|---|
| 型が完全一致 | +100 |
| 引数がすべてスコープから埋まる（入れ子ホール無し） | +40 |
| **ホール名と候補名の一致**（`??config` ↔ `config`） | +25 |
| **命名規則との整合**（`try_`→Result, `is_`→Bool, `get`→Option） | +20 |
| 効果ゼロ | +15 |
| AST節点あたり | −6 |
| 入れ子ホールあたり | −25 |
| 後で使う値を消費する | −20 |

最後に**外側の呼び出し先で多様性再順位付け**する。5件が同じ発想の変種では役に立たない。

### 4-1. ⭐ LLM が必要としてIDEが省くもの（4/5が独立に指摘）

**入れ子ホールを持つ骨格**が最大の差である。

```text
client.try_send(request: ??req)
```

完全な式より、**埋めるべき穴が明示された足場**のほうがモデルには有用である。
IDEは「完成した候補」を出すが、モデルは**部分的に正しい骨格**から続きを書ける。

加えて：名前付き引数を綴った形／効果／消費される束縛／**なぜ使えないかの理由**。
IDEは使えない候補を黙って隠すが、モデルには「なぜ駄目か」が要る。無いと同じ誤りを繰り返す。

## 5. 構築順序（5/5 がほぼ同一）

1. 名前解決 → `DefId` とシグネチャ表
2. AST の型 → `Type`（型位置のホールを含む）
3. **本体の双方向検査** ＋ 効果 ⊆ 予算 ＋ 呼び出しの実体化
4. **`Goal` の JSON 出力**（`expected` / `in_scope` / `allowed_effects`）
5. 候補探索（深さ1）
6. 封印された性質と境界構文
7. ムーブ検査・網羅性検査

> **4 の時点で `xenith goals` を出荷する。候補が空でもよい。**
> 「**期待型そのものが主張であり、順位付けは加速装置にすぎない**」（cursor・grok が独立に同旨）

### 完了の定義（grok）

`examples/scores.xn` の `??lookup` に対して `xenith goals` が
期待型 `Result<Player, ScoreError>`、型付きのスコープ、許された効果を出力すること。
**候補は初日は空でよい。期待型とスコープは空であってはならない。**
