# 0005 — 正典フォーマッタの規則

- 日付: 2026-08-01
- 状態: **採択**（ただし §3 は測定による再検討を予定）
- 根拠: 0002 §2「オプション皆無の正典フォーマッタ」— 4モデルとも維持を支持した数少ない草案項目の1つ。

---

## 1. 保証すること

> **同じ意味のプログラムは、必ず同じバイト列になる。**

この保証が欲しい理由は2つ。

1. **AI出力のブレを消す。** 同じ関数を書かせて毎回違う整形が出ると、差分がノイズだらけになり、
   コーパスも学習データとして劣化する。
2. **空白由来の事故を消す。** セミコロンを採用した時点で空白は完全に無意味になった（0003 §3）。
   フォーマッタはその性質を出力側でも固定する。

**オプションは1つも持たない。** 設定可能なフォーマッタは「同じ意味→同じバイト列」を満たさない。

## 2. 規則

| 項目 | 規則 |
|---|---|
| インデント | 空白4つ。タブは出力しない |
| 行幅 | 100桁。超える場合のみ改行形に切り替える |
| 改行コード | 常に LF |
| 末尾 | ファイルは必ず改行1つで終わる |
| トップレベル項目の区切り | 空行ちょうど1つ |
| ブロック内の空行 | **すべて削除**（§3） |
| 複数行リストの末尾カンマ | 常に付ける（1行に収まる場合は付けない） |
| コメント | 位置を保って出力する。**1つでも失われたら整形を中止する**（§4） |

## 3. ブロック内の空行を削除する（意図的に強い規則）

これは他の主要なフォーマッタ（gofmt、rustfmt）と**異なる**選択なので、理由を残す。

空行は意味を持たない。したがって「同じ意味→同じバイト列」を**文字どおり**満たすには、
空行の有無で出力が変わってはいけない。空行を1つに畳むだけの規則では、
「空行を書くモデル」と「書かないモデル」で出力が割れ、§1 の目的1が達成できない。

代償は、長い関数の視覚的なグループ分けが失われることである。
これは「関数が視覚的グループ分けを必要とするほど長いなら、分割すべきだ」という立場を取る。

> ⚠️ **これは仮説であり、測定で再検討する。** `bench/ai/` が動いた時点で、
> 空行を残す方言と削除する方言の両方で pass@1 を測る。
> 可読性の低下が実際にモデルの成績を下げるなら、この規則は撤回する。

## 4. フォーマッタは自分の出力を検証する

整形は意味を変えてはならない。意味を変えうるフォーマッタは、無いより悪い。
そこで `format` は出力を返す前に自分自身を検査する。

1. **出力を再び字句解析し、意味を持つトークン列が入力と一致することを確認する。**
   種別だけでなく綴りも比較する。
2. **コメントが1つも失われていないことを確認する。**

どちらかが破れた場合、**整形結果を返さずエラーを返す**。これはフォーマッタのバグであり、
利用者のソースを壊すより、整形を拒否して報告するほうがはるかにましである。

同じ理由で、**構文エラーを含む入力は整形しない**。解析できないものは正しく整形できない。

## 5. 冪等性

`format(format(x)) == format(x)` はテストで強制する。
冪等でないフォーマッタは、保存のたびに差分を生み、CIを不安定にする。

## 6. v0.0 の既知の制限

- 式の改行は呼び出し引数のみ。長い二項演算の連鎖は1行のまま100桁を超えうる。
- コメントは「直前の項目・文の前」に寄せて出力する。式の途中に書かれたコメントは
  位置がずれる。§4 の検査により**失われはしない**が、意図した位置には戻らない。

どちらも整形の質の問題であって、正しさの問題ではない。改善は後続の版で行う。
