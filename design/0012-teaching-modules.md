# 0012 — 診断がモジュールを教える（採択版）

- 日付: 2026-08-08
- 状態: **採択（5モデル並列レビュー後の改訂版）**
- 手法: 事前登録 → codex(gpt-5.6-sol xhigh) / grok(4.5) / agy(gemini-3.1-pro-high) /
  opencode(gpt-5.6-sol xhigh) / cursor(grok-4.5) の5並列攻撃 → 判定統合。
  **草案は3点で大破**: (1) P2/P3 を測定前に実装する順序は実験汚染（codex/opencode/cursor
  最危険同着）→ **本 RFC は P1+P4 に縮小、MCP と api 製品化は 0013 へ分離**。
  (2) 「型がシグネチャに現れる」フィルタは 0009 で葬った producers の別経路再導入（5/5）。
  (3) 反証→UFCS 直結は測定失敗を言語変更で上書きする悪例（5/5 棄却・段階化へ）。

## 1. P1 — ModuleCall teach（XN2003 のモジュール API 拡張）

対象: **呼び出し位置の XN2003** でレシーバの名目型が解決可能なモジュール所有型のとき。
型変数・解決不能なら添付しない（偽橋を出さない — cursor）。

- **所有モジュール** = 型を定義するモジュールのみ（0010 に re-export は無い）
- **候補** = 所有モジュールの pub fn のうち、エイリアス解決後のレシーバ型が
  **入力引数に直接現れる**もの。**戻り値のみの一致は除外**（producers 削除の教訓を貫徹 — 5/5）
- **順位（決定的）**: (a) fn 名が未知メンバー名と完全一致 — **一致候補は必ず枠内**
  （押し出し不変条件・枠は増やさない — grok） → (b) 第1引数型が一致 →
  (c) その他の入力位置 → 同点は完全修飾名の辞書順
- **提示 = 書き換え橋**（シグネチャ列挙で止めない — 5/5）。新 TeachKind::ModuleCall:
  `callee` / `receiver_parameter` / 完全シグネチャ（**型も完全修飾**: `depot.locker.Locker`）/
  `rewrite`: `depot.locker.stow(locker: <receiver>, load: ...)`。
  複数の入力位置が適合する場合は rewrite を出さずシグネチャのみ（誤誘導防止 — codex/opencode）
- **診断本文も直す**: モジュール所有型では「has no method named `stow`」で止めず、
  「モジュール関数は `depot.locker.stow(...)` として呼ぶ」を本文に一文（メソッド事前分布を
  本文が強化しない — grok）
- 予算: 0009 と同一の定数を再利用。**署名をバイト途中で切らない** — 候補単位で
  収録/省略し、省略数を構造化して返す。重複排除キーは（型, 未知メンバー名）
- `--diagnostic-teaching=off` はバイト同一（0009 契約）。golden:
  `locker.stow(load: 12)` → teaches に `depot.locker.stow(locker: ..., load: ...)` が含まれる
- **正直な限定（agy の急所への回答）**: 本機構は rounds-to-green を狙う。診断は初回失敗の
  後にしか届かないため、**このパターンの pass@1 は構造的に改善しない** — pass@1 は
  文書（api 地図）の領分であり、P4 から pass@1 の主張はしない

## 2. P4 — 検証測定（手順隔離つき・84走）

- **順序: P1 実装 → 即測定。** 測定ブランチには P1 以外の変更を入れない
  （MCP 不変・ツール表面不変・プロンプト/課題/文書は 0011 凍結のまま）
- 腕: `t5v2-none-on` / `t5v2-none-off`（7モデル×6課題×2腕 = 84走・新条件名・0011 結果不変）
- **操作確認（「ほぼ」禁止 — grok/cursor）**: t5v2-none-off の診断は teaching ブロックを
  除き 0011 none-off とコード・本文一致であること。ずれたら測定前に止める
- **配達監査（codex/grok/opencode）**: 各走で「正解 fn が候補集合に生成されたか /
  予算内に残ったか / 実際に feedback に載ったか」を台帳に記録。効果ゼロのとき
  「モデルが使わなかった」と「配達されなかった」を区別できない測定はしない
- 主エンドポイント: **t5a の課題単位・対応あり比較**（rounds-to-green 分布と最終緑）。
  6課題プールで希釈しない（grok）。副: t5b は回帰監視のみ
- 条件付き延長を事前登録: none 対で信号があれば api 対（+84走）で代替/補完
  （0011 H4 の後継）を測る。無ければ配達監査の検分が先
- **反証の段階化（UFCS 直結の削除 — 5/5）**: 改善なし →
  (A) 配達監査を検分（未配達なら抽出/予算の欠陥＝0012bis で修理） →
  (B) 配達済みで不使用なら提示形式の改訂（書き換え例の強化）を 0012bis →
  (C) 設計空間を使い果たして初めて、言語側（メソッド風糖衣の解決規則・曖昧性・評価順）を
  **問題設定として** 0014+ に登録。改善なし ≠「診断で橋は架からない」の証明

## 3. 0013 へ分離した議題（レビューの設計制約つきで登録）

- **MCP プロジェクトモード**: 共有 ProjectSnapshot（CLI/MCP 単一実装）・要求に
  `mode: auto|project|single_file` と明示 root・**発見失敗は明示エラー**（無言フォールバック
  禁止）・推移的全ファイルの封じ込め検査・応答に実際の analysis_mode/root を返す・
  同値検査は**正規化診断オブジェクト**（code/severity/span/message/teaches）であり
  生バイトではない・単一ファイル要求へのカスケードエラーの絞り込み（agy）
- **`xenith api` 製品化**: 共有すべきはレンダラではなく **ApiSurface 意味モデル**
  （text/JSON/ベンチ dump はその別レンダラ）・JSON は独立 schema_version を payload に
  内蔵・モジュール/型/シンボル単位の絞り込み照会（全量 dump はトークン限界を割る — agy）・
  MCP 露出は experimental 隔離で既定ツール一覧に載せない・ツール説明に
  「配線の代替ではない（0011 で 0/28）」を明記（grok）
- XN7008 null 観測点の罠再設計（リスク登録として持ち越し）

## 4. 入れないもの

- guide / api-dump / 課題 / プロンプトの変更（0011 凍結の維持）
- 0009 予算数値の変更（新しい数の発明禁止）

## 5. 却下された草案要素（記録）

- 「型がシグネチャに現れる」フィルタ — 戻り値のみの factory や別位置引数まで拾い、
  正解を予算外へ押し出す。producers 削除（0009）の自己否定だった
- シグネチャ列挙のみの提示 — 橋の半分。レシーバを第1引数へ移す操作が伝わらない
- CLI/MCP 生バイト一致 — 表面形式の偶発同値を固定する誤った検査単位
- P2/P3 の同時実装 — none 腕の環境が 0011 と別物になり P1 に帰属できない
- 反証→UFCS 直結 — 検出力不足の偽陰性が 0010 の中核を政治的に揺する構造
