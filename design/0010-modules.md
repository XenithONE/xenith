## 0. 判定の要約

| 事前登録 | 判定 |
| --- | --- |
| P1 ファイル=モジュール・`mod` 無し | ✅ 5/5 — ただし正規化・ルート・エントリ規則を §2 で厳密化 |
| P1 マニフェスト（name 必須） | ⚠️ ルートマーカーに降格、`name` は任意 |
| P2 項目 use とモジュール use の二本立て | ❌ 5/5 — 「1つの書き方」を自ら破っていた。§3 へ置換 |
| P3 既定私有 + `pub` | ✅ 5/5 —「全部 public + 規約」はコンパイラが強制できない“お願い” |
| P3 pub struct = 全フィールド pub | ⚠️ 修正 — 境界を越える mutation を禁止（§4） |
| P4 import 循環の全面禁止 | ❌ — 「単一パス実装の都合の仕様昇格」（codex）。§5 へ置換 |
| P5 use-fix teaches | ✅ 方向は 5/5 — ただし一意時のみ auto-fix・二層候補空間（§6） |
| P6 順序 | ❌ — 仕様と適合テストが先、use-fix は解決と同一スライス |

**最危険の見落とし（codex / agy が同着）**: 草案の `use a.b.c;` は「モジュール
`a.b.c`」とも「モジュール `a.b` の項目 `c`」とも読め、ファイル追加だけで既存
ソースの意味が変わり得た。局所完結性・決定性・先行グラフ構築が同時に崩れる。
§3 の設計はこの曖昧性を**構文レベルで根絶**する。

## 1. 中核決定 — `use` は依存宣言、参照は常に完全修飾

```xenith,planned
use game.player;
use game.scores;

fn award(p: game.player.Player) -> Int uses {} {
    game.scores.best(player: p)
}
```

- **`use` が取るのはモジュールパスのみ**。項目 use・グロブ・`as` は存在しない
- **他モジュールの項目への参照は常に完全モジュールパス**（`game.player.Player`）。
  短縮束縛は作らない — 最終セグメント束縛（`player.Player`）でも
  `a/model.xn` と `b/model.xn` の `model` が衝突する（codex の反例）。
  完全修飾なら同名項目の衝突が**原理的に存在しない**ため、エイリアスも不要
- `use` していないモジュールの項目参照はエラー（機械適用 fix が use を挿入 — §6）
- **未使用 `use` はハードエラー**（grok — 「候補を全部 use する」を成功戦略に
  させない。ファイルの use リスト = 正確な依存リスト）
- 同一実体への綴りは常に1つ。診断・goals・producers・検索の正規形が保たれる

## 2. ファイル = モジュール（P1 の厳密化）

- 1ファイル = 1モジュール。ファイル内 `mod` 宣言・`mod.xn` は存在しない
- **ソースルートは `src/`**。`src/game/player.xn` → モジュール `game.player`。
  `src/` 外の `.xn`（examples・生成物・ベンチ）はモジュール候補にならない（codex）
- **エントリポイントは `src/main.xn`**（モジュール名 `main`）。`fn main` は
  ここにのみ書ける。他モジュールの `fn main` はエラー（opencode の最危険指摘への回答）。
  ライブラリプロジェクト（main 無し）は `check` は通り `run` が明確なエラー
- **パスセグメントは `lower_snake` の識別子のみ**（`player-v2.xn` は拒否）。
  大文字小文字だけ異なるファイルは**ホスト OS に関わらず拒否**（Windows の
  非区別で決定性が壊れるのを防ぐ — opencode/grok/codex）。シンボリックリンク・
  ネストしたマニフェストは拒否
- **モジュールパスとトップレベル項目名は同一親の下で排他**: `game.xn` が
  `pub player` を持ち、かつ `game/player.xn` が在る構成はグラフ構築時エラー
  （cursor）。§1 と併せて `a.b.c` の読みが常に一意になる
- **1ファイルに複数の pub 型・関数は合法**（grok —「1ファイル1型」の誤学習防止に
  ガイドで明記）
- マニフェスト `xenith.toml` は**ルートマーカー**。`name` は任意（将来の
  パッケージ ID 予約と明記し、解決には使わない）。マニフェスト無しの
  単一ファイル起動は従来どおり（後方互換）
- **`std` はプロジェクトグラフ外の封印仮想名前空間**としてルート名 `std` を予約。
  プレリュード（Option/Result/List/Map/String/Io/empty_map）は従来どおり use 不要。
  **現行ガイドと examples の `use std.io;` は儀式的な嘘だった**（grok の表）ので
  本スライスで削除する。将来 std に実モジュールが載るときは `use std.x;` が
  本物の依存宣言になる

## 3. `use` の構文と意味（P2 の置換）

- 構文: `use <module-path> ;`（既存のパーサが受理する形のまま）。ただし
  意味論は「そのモジュールへの依存を宣言し、完全修飾参照を許可する」
- 解決: パスはソースルートからのモジュールパスとしてのみ解釈（§2 の排他規則で
  一意）。存在しないモジュールは専用診断
- フォーマッタ: use 群はファイル先頭・辞書順・重複除去を正典とする
  （「機械適用 fix の挿入位置」の正規形でもある — codex）

## 4. 可視性（P3 の修正）

- トップレベル項目（fn / struct / enum / const）は**既定で同一モジュール私有**。
  親・子モジュールへの特権は無い（codex — 最も局所的な規則）
- `pub` で公開。`main` は pub 不要の特別扱い
- **公開 API 閉包検査**: `pub fn` のシグネチャ・`pub struct` のフィールド型・
  `pub enum` の payload 型に私有型が現れたらエラー（codex）
- `pub enum` は全バリアントが外部から構築・match 可能（明記 — grok）
- `pub struct` は外部から**構築・読み取り・パターン分解が可能**。ただし
  **モジュール境界を越えるフィールド代入は禁止**（`var` フィールドでも外部からは
  `p.score = …` 不可 — 変更は所有モジュールの pub fn 経由）。構文は増やさず
  規則1つで不変条件の壁を作る（grok 案を採択。codex の「表現公開は強い約束」への
  回答でもある — 表現は見せるが書き換えは見せない）。緩和は後方互換だが逆は
  破壊的なので、厳しい側から始める
- 私有項目への外部参照の診断から「`pub` を自動挿入する fix」は**出さない**
  （公開 API 化は局所的な構文修正ではない — codex）

## 5. モジュールグラフと検査順（P4 の置換）

- **import 循環は禁止しない。** Xenith にモジュール初期化文は無く、宣言の相互参照は
  実行順問題を持たない。全面 DAG 要求は「単一パス実装の都合の仕様昇格」であり、
  循環診断は AI に局所修復不能な「ファイルを再分割せよ」を突き付ける（codex）
- 検査は二相: (1) 全ファイルの宣言ヘッダを索引化 → (2) 本体を検査。
  順序はモジュールパスの**辞書順**で決定的（「トポロジカル順だから決定的」は
  誤りだった — opencode。同順位タイブレークを明示）
- 拒否するのは**意味的循環のみ**: 値として自分を含む無限サイズ型・const 初期化の
  循環。それぞれ専用診断
- 診断コードは「2つ」と事前固定しない（codex）: 不明モジュール・不正パス・
  モジュール/項目名衝突・私有参照・公開 API 閉包違反・エントリ違反・未使用 use・
  大小文字衝突は**別の失敗**であり、必要な数だけ xenith-diag の規律で追加する

## 6. 診断とツール（P5 の分割）

- **XN2002 の use-fix**: 綴りが**完全一致**する pub 項目がプロジェクトに一意に
  在るときのみ、機械適用 fix「`use game.player;` を挿入」を出す（挿入位置は §3 の
  正典順）。複数在るときは正規モジュールパス順の**候補列挙のみ**（fix なし・
  フォルダ距離等のヒューリスティック禁止 — codex）。ローカル名のタイプミス候補
  （did-you-mean）とは診断上分離
- **候補空間の二層**（codex）: 既定の `goals` / `producers` / teaches は
  **現在のスコープ（use 済みモジュール + プレリュード）のみ**。プロジェクト全体の
  pub 項目は「use の編集レシピつき」の明示照会（別コマンド/別節）でのみ返す —
  「利用可能な式」と「import すれば利用可能になる式」を混ぜない
- use-fix は**名前解決と同一の垂直スライスで出荷**（cursor — 最初の複数ファイル
  体験を「エラーは出るが直し方は推測」にしない）

## 7. 実装順序（P6 の置換 — codex 案を基に）

1. 仕様の適合テストを先に置く: モジュール ID 正規化・ソース集合・エントリ規則・
   排他規則・大小文字拒否の**正例と負例**
2. `pub` の構文追加（**パーサ変更は在る** — 「無し」は草案の誤り）と
   マニフェスト読込・ファイル索引・宣言ヘッダ索引を2ファイル E2E で通す
3. use 解決・私有検査・公開 API 閉包検査・未使用 use・排他規則 —
   **XN2002 use-fix を同スライスに含む**
4. 二相検査の統合（宣言索引 → 本体、辞書順）と意味的循環の専用診断
5. examples を複数ファイル構成に拡張・ガイドから `use std.io;` の儀式を除去・CI
6. tier-5 課題と retrieved 条件は次の測定 RFC（本 RFC の範囲外）

## 8. 入れないもの（レビュー同意済みの線引き）

パッケージ間依存・バージョン解決・std の物理分割・自己ホスト・re-export・
グロブ・`as` エイリアス・フィールド単位の可視性構文・条件付きコンパイル・
テスト特権（テストは同一ファイル内 or pub API 経由 — 制約として明記）。
ルート名前空間は `std` に加えて将来の依存パッケージ用に「ローカルと構文上
区別できる余地」を予約する（先頭セグメントの衝突を今固定しない — codex）。

## 9. 却下された代替案（記録）

- **項目 use（`use game.player.Player;`）** — モジュール use との二本立ては
  原則3違反（5/5）。単独形としても `User` vs `User` の衝突にエイリアス無しでは
  詰む（codex の表現力欠落の証明）
- **最終セグメント束縛（`use game.scores;` → `scores.best`）** — `a.model` と
  `b.model` で束縛が衝突。完全修飾のみが衝突ゼロ
- **`as` エイリアス** — 同一実体の綴りを増やす。完全修飾で不要になった
- **import 循環の全面禁止** — 実装都合の仕様化。二相検査で不要
- **「全部 public + 命名規約」** — コンパイラが強制できない規約は AI も人間も破る
- **pub フィールドの外部 mutation 許可** — capability/効果で副作用を縛る言語が
  データ不変条件だけ裸にするのは整合しない
- **`mod` 宣言 / `mod.xn`** — ファイルシステムとの二重真実源
